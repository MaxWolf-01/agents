3. Coarse to concrete: the spec's sections are the resolution ladder

Your question: how does idea-finding go from coarse to detailed, and how do we want it to? The spec template already encodes an answer, read top to bottom. Each section is one resolution step; a session reads down only as far as it needs, and writes only the sections its decisions touch. That is what the map's "low-res view" was doing by hand.

(my call) The frontier moves down this ladder mostly, never strictly: a concrete finding (a prototype verdict, a library limit) can reopen a story, which is what the accent arrow in the proposed flow is. The ladder is the reading order for a fresh session, not a waterfall for the writing.

(my call) A session's low-resolution view is Problem, Solution, the marks in Implementation Decisions, Further Notes, plus the open tickets from the tracker. That is the map body, section for section, and it is the top and bottom of the spec. The middle (stories, properties, the decisions' detail) is read when a ticket touches it. Stated in grilling as "read the spec top-down; a decision ticket names the sections it may rewrite".

(my call) Domain-agnostic by omission: a section with nothing to say is left out, and a template note says so. Course content skips Testing Decisions; a data migration skips User Stories or writes two. Upstream's template is software-first because Pocock's is a software workflow; the sections that carry the planning are not.

4. The frontier: what this round asks

❓ Q1: Is "the spec read top-down + open tickets" enough of a low-resolution view, or does a big feature need a stated index?

➡️ (a) enough: reading order in grilling, no new artefact; the marks are the index

(b) keep an index, as a ## Decisions list at the top of the spec: one line per settled decision, link to the ticket

💡 (a) keeps one home per fact; the moment an index exists someone updates the spec and not the index. The cost is that a 400-line spec has no one-screen summary. (b) is the map's index kept inside the spec; cheaper to scan, and exactly the copy that went stale in the skilltree map. If (a) reads badly on a real big spec, (b) is one round away.

❓ Q1b: Domain-agnostic by omission, or a second template?

➡️ (a) one template, sections omitted when empty, one sentence saying so

(b) a planning-only template (Problem, Solution, Stories, Decisions, Out of Scope, Further Notes) for non-software efforts

💡 (a) because nobody has run a non-software effort through mx yet; a second template is speculative generality. (b) becomes right the first time a course-content grilling actually runs.

❓ Q2: Where do the map's Notes go (skills every session should consult, standing preferences)?

➡️ (a) project CLAUDE.md: they are per-project navigation, which is what that file is for

(b) a short ## Notes section in the spec

💡 (a) because in skilltree the map's Notes were project-wide ("use these skills", "these preferences"), not feature-wide; (b) wins if a feature genuinely wants preferences its project doesn't share.

❓ Q3: Where does "refer by name, never by bare id" live?

➡️ (a) writing-for-humans: it is a reader-facing rule about any artefact text

(b) tracker: it is about tickets specifically

💡 (a) because the rule bites in chat narration and commit messages as much as in tickets, and writing-for-humans is what code-review already applies to every diff.

❓ Q4: What becomes of the wayfinder skill file?

➡️ (a) delete it; orient and README say "grilling spans sessions when it has to"; the trigger words (wayfinder, charting, map) go into grilling's description for one release, then out

(b) keep a stub skill that loads grilling

💡 (a) because a stub is a second name for one thing, which is this whole session's lesson; the description carries the old words for discoverability without a second file. Upstream has a wayfinder skill; pocock-sync's mapping records it as dissolved, like to-spec.
