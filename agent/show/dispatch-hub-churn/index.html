Five tickets, one file,
the same two hunks.

The rebase churn isn't bad luck and it isn't 20 tickets colliding at random. A handful of files absorb an edit from nearly every ticket. Those are the hub files, and there are exactly two ways out: make tickets take turns on them, or make tickets stop needing them.

======= why they conflict

Every ticket writes to the same two places

Here is the real App.svelte, with the ticket that added each line. It is 57 lines long and five tickets edited it — but not five different regions. Two: the import block and the panel column.

Git conflicts on adjacent lines, so five tickets appending to one sorted import block is close to a guaranteed collision. Each ticket's own diff looks fine in review — one import, one tag. Only the orchestrator, watching tickets converge, can see the file is a hub at all.

>>>>>>> two ways out

Take turns, or stop needing to

Same problem, two different levels. One is a scheduling rule; the other deletes the hub.

DOOR 1 — take turns (scheduling)

A hub file is a lock: at most one in-flight ticket may hold it. Everything that doesn't touch it still runs in parallel. That's a much weaker condition than the current rule, which asks for fully disjoint file sets and therefore never fires.

Ticket 19 starts later and finishes earlier, because it never pays for two rebases. Tickets 16 and 22 are unaffected — the lock is per file, not per wave.

DOOR 2 — stop needing to (structure)

The hub exists because the panel list is hand-maintained. Make the list something the app discovers, and a ticket adds its own file instead of editing a shared one.

Ticket 15 and ticket 19 now write to different paths that have never existed before. The merge is trivial by construction. Same move for http.ts (route modules) and serve.ts (command table).

<<<<<<< how they fit together

The probe decides which door

They aren't alternatives so much as a threshold. The measurement in section one is what tells you which you're in:

2–3tickets on a filetake turns — the lock costs one delayed spawn
4+tickets on a filebuild the seam — the lock would serialize the feature

Above the threshold the lock stops being a scheduling tweak and becomes a queue: with five tickets waiting on http.ts, taking turns is just dispatch doing serial work in an expensive way. That's the point where a seam ticket lands first, alone, and the wave behind it runs wide.
