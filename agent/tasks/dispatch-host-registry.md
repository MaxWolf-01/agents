# Dispatch picks a worker host from a registry, not from an env var

## Context

Dispatch currently learns its worker host from `$MX_WORKER_HOST`, one value set
per laptop in Home Manager. That hardcodes a single host into the environment:
adding a second machine means editing nix and re-switching, and a dispatcher
cannot see that its host is down until an ssh fails.

The per-host half of the answer already exists. Each worker host publishes
`~/HOST.md` — toolchain and limits, generated by that host's own config, so it
cannot drift from what is installed (see `dispatch-agent-user.md`). What is
missing is the index over those: which hosts exist, which are up, and which one
this run should use.

Decided by max, 2026-08-25, in conversation:

- The host list lives in the **secrets** repo — tailnet addresses and machine
  inventory are not public.
- Each entry carries a **hand-written description**, not only generated facts:
  what the machine is for and what its uptime is like.
- Dispatch **looks the hosts up at the start of a run** and chooses one. When
  the chosen host goes down mid-run, dispatch restarts on another or waits for
  a human to fix it — no failover machinery.
- This **supersedes `MX_WORKER_HOST`**, which is removed once the registry
  lands.

## What to build

A command that answers "which host should this run use", and a dispatch setup
step that calls it instead of reading an env var.

**The registry** — the host list in `secrets/`, one entry per machine: address,
the hand-written description, and whatever else selection needs that isn't
already in that host's `HOST.md`. Generated capability facts stay in `HOST.md`;
the registry points at hosts, it does not describe their toolchains.

**The command** — prints one block per host: name, reachable or not, the
description, current utilization fetched live (load, free memory, free disk;
GPU where there is one), and the host's limits. Probes run in parallel — a
down host must cost a timeout, not a hang, and not delay the others.

**Dispatch** — setup step 4 stops reading `$MX_WORKER_HOST` and reads the
registry instead: report the candidates to the user with their state, pick
one, and record it as `worker-host:` frontmatter in the feature's
`needs-human.md` as it does today.

## Open questions

- **Where the command lives.** `~/.dotfiles/bin` makes it max's tool on max's
  machines; the mx plugin makes it portable but leaves it with no host list to
  read on anyone else's machine. A third shape: the plugin describes the
  contract ("a registry command prints these fields") and the environment
  provides the implementation.
- **How much the command fetches.** Reachability alone is one round trip per
  host; utilization and `HOST.md` are more. Whether the expensive fields are
  default or opt-in depends on how slow the full sweep turns out to be.
- **What dispatch does with more than one usable host.** Pick by declared
  capacity, ask the user, or spread a wave across hosts — the last one changes
  the mechanics section, since worktrees and bare repos are per host.

## Acceptance criteria

- [ ] The command lists every host with its state, description and limits, and
      a down host returns a result instead of hanging.
- [ ] Dispatch's setup names the hosts it saw and which it chose, with no
      reference to `$MX_WORKER_HOST`.
- [ ] `MX_WORKER_HOST` is gone from `nix/home/hosts/*.nix` and from every skill.
- [ ] A host added to the registry is usable by dispatch without a nix rebuild.

## Out of scope

- Failover or migration of a running wave to another host.
- Scheduling across hosts (a wave stays on one host).
- Anything about what a host *can* do — that is `HOST.md`, already built.
