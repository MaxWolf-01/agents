# Dispatch picks a worker host from the machines that have one, not from an env var

## Context

Dispatch learns its worker host from `$MX_WORKER_HOST`, one value set per laptop
in Home Manager. That hardcodes a single host into the environment: adding a
second machine means editing nix and re-switching, and a dispatcher cannot see
that its host is down until an ssh fails.

The per-host half of the answer already exists. Each worker host publishes
`~/HOST.md` — toolchain and limits, generated by that host's own config (see
`dispatch-agent-user.md`). What is missing is the index over those: which hosts
exist, which are up, and what each one is currently carrying.

Decided by max, 2026-08-25 and 2026-08-27, in conversation:

- **Worker hosts only.** The tagged VPSes (`jarvis`, `yapit-prod`) are never
  candidates, so nothing about them belongs here.
- **No list file.** The set of worker hosts is every
  `nix/home/hosts/<name>-agent/HOST.md` in `~/.dotfiles`. Adding a machine is
  adding its Home Manager config, which is required anyway — a separate list
  would be a second place to forget. `bin/backup-hosts` reads its host list out
  of the nix files for the same reason.
- **`HOST.md` becomes hand-written**, with one token substituted by nix for the
  generated toolchain line. Its lead paragraph is free-form: what the machine is
  for, its uptime character, and any guidance that is not mechanical.
- **Dispatch looks the hosts up at the start of a run** and chooses one. When
  the chosen host goes down mid-run, dispatch restarts on another or waits for a
  human — no failover machinery. Nothing reachable means workers run locally, as
  they do today.
- **This supersedes `MX_WORKER_HOST`**, which is removed everywhere it appears.

## What to build

**The record.** `nix/home/hosts/<name>-agent/HOST.md` in `~/.dotfiles` is
hand-written: frontmatter (`host`, `user`, `isolated`), a free-form lead
paragraph, and the sections a worker reads. A `@TOOLCHAIN@` token is substituted
by that host's `.nix` from the package list it installs, so the toolchain line
still cannot drift from what is there. The host publishes the substituted file
as `~/HOST.md`; the hand-written original stays readable in `~/.dotfiles`, which
is what lets a down host still describe itself.

**The command.** `bin/worker-hosts` prints one block per host: name,
reachable or not, the lead paragraph, and live state. Probes run in parallel
with a connect timeout — a down host costs a timeout, not a hang, and does not
delay the others. `worker-hosts <name>` prints that host's whole record.

State it reports, per host:

- **Load**, the 5-minute average over the core count. An instantaneous figure
  misleads.
- **Memory**, `MemAvailable` plus the ZFS ARC where `arcstats` exists — ARC is
  evictable but counted as used, so `MemAvailable` alone understates a ZFS
  host's headroom by gigabytes.
- **Disk**, `df` of the paths a worker writes — its home and `/tmp` —
  deduplicated by filesystem. Nothing enumerates disks: a pool the worker user
  cannot write to never appears.
- **GPU**, utilization and free memory where there is one.
- **Running workers**, session name and worktree directory, filtered to
  dispatch's own sessions.

**ssh.** `pc` gets a `programs.ssh.settings` entry in `common.nix` carrying its
tailnet address, as every other tailnet host already has. Without it the name
resolves through whatever DNS answers — on the home LAN, the router's address
for it.

**Dispatch.** Setup stops reading `$MX_WORKER_HOST`: it runs `worker-hosts`,
reports the candidates with their state, picks one, and records it as
`worker-host:` frontmatter in the feature's `needs-human.md` as it does today.

**Session namespacing.** Worker tmux sessions and channels are
`dispatch-<feature>-<NN>`, so two dispatchers running same-named features in
different repos collide on both the session name and the `/tmp/<channel>.*`
files. Worktree paths and ticket branches are already namespaced against this;
sessions were missed. They become `dispatch-<repo>-<feature>-<NN>`.

## Acceptance criteria

- [ ] `worker-hosts` lists every host with its state and lead paragraph, and a
      down host returns a result instead of hanging.
- [ ] A host that is down still shows its lead paragraph.
- [ ] Dispatch's setup names the hosts it saw and which it chose, with no
      reference to `$MX_WORKER_HOST`.
- [ ] `MX_WORKER_HOST` is gone from `nix/home/hosts/*.nix` and from every skill.
- [ ] A machine given a `<name>-agent` Home Manager config appears in
      `worker-hosts` without any other edit.
- [ ] `ssh pc` reaches pc's tailnet address rather than whatever DNS answers.
- [ ] Worker sessions and channels carry the repo name.

## Out of scope

- Failover or migration of a running wave to another host.
- Scheduling across hosts (a wave stays on one host). Where more than one host
  is usable, dispatch takes one; a preference belongs in a host's lead
  paragraph, not in a scheduler.
- Anything about what a host *can* do — that is `HOST.md`, already built.
