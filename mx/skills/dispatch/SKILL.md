# Dispatch

You are the **single orchestrator** of one ticket's child tickets: compute the frontier, fan a **wave** of workers out, integrate tickets as they **land**, repeat until none are left open. One worker works one ticket; dispatch orchestrates N workers. You are the only writer of a ticket file here, the only holder of the branches the workers merge into, and the one that writes `done`, on the user's accept. A project is two repos, the code repo and the agent repo it holds at `agent/` (`/mx:tracker`), and a ticket is worked in both: `dispatch` cuts, pushes and fetches a `ticket/<slug>` branch in each, and you merge both.

Dispatch is the one way tickets are worked, at any size: every ticket goes to a worker, and a ticket with no child tickets is one worker's whole job. The `blocked-by` DAG is what makes independence explicit.

With a wave size of one the same loop runs **serially**, the common case: the orchestrator role (frontier bookkeeping, the pre-merge read, integration, status, QA hand-offs) is what a two-ticket tree gets from dispatch, and serial is the right mode for surface-heavy waves (see the coherence test below).

Two scripts beside this skill carry the mechanics, and each one's `--help` is its reference. `dispatch` runs here, on the branch the ticket branches cut from, and is the one command you type for a worker host: `dispatch ctl <args>` runs `dispatch-ctl` on the host that ticket's spawn named (this machine, or one over ssh), which owns the ticket worktrees, branches, sessions and run state there. History stays here: commits, merges, pushes and fetches are yours. `run-worker.sh` is the in-pane runner and the only file that names a harness; a different one (`codex exec`, a container) is a sibling runner passed via `DISPATCH_RUNNER`.

## Setup (once)

1. Fetch the ticket and its child tickets per `/mx:tracker`.
2. **The ticket you are working holds the branch its children merge into**, in its own worktree of the code repo. Cut both from the branch above it, its parent ticket's or the integration branch (`git worktree add ../<repo>-<slug> -b <slug>`); the checkout you were invoked in never switches branches. That worktree has no `agent/` in it and needs none: the agent repo keeps the branch its main checkout has out, ticket files are written there, and `dispatch` finds it from either. Child ticket branches cut from it and merge back into it; the branch above sees the whole tree as one `--no-ff` merge when the ticket ships. A ticket with no children of its own has neither branch nor worktree to cut: you dispatch it from the checkout you are in, on the branch its ticket branch cuts from and merges back into at the ruling (tick step 1).
3. **One orchestrator per tree, and check the neighbours.** Other orchestrators may run concurrently on other trees. Before the first wave, read the tracker for other open and claimed tickets. A `blocked-by` edge reaching out of this tree is a hard serialize signal: mechanical, and `tracker frontier` names it. Beyond that, judge: where another tree's design space or file surface overlaps this one's, warn the user and let them decide whether to serialize; small merge conflicts at integration are fine, a shared design space is not (that's one piece of work wearing two names).

## The tick

### 1. Integrate what landed

Open the tick with `dispatch ctl probe`: it decides who exited.

For each worker that has exited, `dispatch fetch <slug>` brings both its ticket branches here, the code repo's and the agent repo's, and the **report** the second carries at `agent/show/<slug>/report.md`. The report is the worker's finished signal, and the probe line says whether this round committed one (`report=yes`), which on a resume is a report that differs from the one the round before it left:

- **No report** → the run left nothing to review, its in-pane retries already spent. `dispatch ctl log <slug>` shows how it ended and why, in the worker's own words: the chunk it was on, and the line it wrote on the way out. Scrollback is the fallback when that log is silent (Observe, below); where neither explains it, report the cause as unknown rather than guessing one. A permission denial or a spent usage limit is a first-class resumable event: clear the blocker (add the allowlist entry it needed, wait out the reset) and resume.
- **A report** → it alone proves nothing. Read both ticket branches' diffs against the ticket and its ancestry first: you hold the whole tree where the worker held one ticket, so a detail its brief missed is yours to catch; what you find goes back to the worker as guidance on resume, or becomes a proposed ticket (`/mx:tracker`). Two findings in that read are not judgement calls. A change under the project's properties directory (`tests/properties/`), in any ticket but the one that builds them, goes back to the worker unmerged, since a slice that edits a property passes by weakening what the property was there to hold; the one edit that merges is the deletion of the expected failures naming this ticket (`/mx:testing`), and a diff that is anything beyond those deletions goes back whole. And an expected failure in the ticket branch's tree that still names this ticket goes back the same way, whatever the suite says, since the slice has not made its property hold: grep the properties directory for the ticket's slug, because one the worker never touched is absent from its diff. Then `dispatch review <slug>`: it imports the report into the ticket, which is where the worker's closing comment, questions and assumptions enter the tracker, renders the ticket's page over both unmerged branches, flips the ticket to `review`, and stages the ticket's demo unrun in a tmux session with those branches checked out beside this worktree (`dispatch --help`); the build waits there for the user's ruling, and the staging waits with it until `dispatch ctl cleanup` or the next round's `dispatch fetch`. **A speculative build merges nothing until the user rules**: the ticket branch is its container, the branch you hold carries only ruled-in work, and a ticket in `review` unblocks nothing. Tick the acceptance criteria the build meets as you read it, in the tracker's copy: the report names the ones it claims and the ticket file is yours to write. Then announce it: relay the worker's closing comment and the ticket's open questions as they stand (their `[Dn]` tags renumbered to continue this session's, and where a note on the page cites a tag it is the ticket's own numbering, so say which is which), open the review page, and name the session the demo waits staged in, which the user presses Enter on when they choose. You run no demo yourself. A demo that is missing, that the worker's own run did not carry, or that leaves the user to find the change rather than walking them through it (`/mx:show`), goes back to the worker before the ruling, as a missed acceptance criterion does; a Demo line saying the diff is the demo is complete as it stands. The board's needs-me group is where the ruling waits, those questions under its row. **An answer the user gives you is yours to record**, `tracker rule` on the ticket. A question the ruling leaves open is filed as a proposed ticket as you write that ruling, so the ticket reaches `done` carrying none. The ruling's four outcomes are `/mx:tracker`'s; here is what each one runs:
  - **Accept** → merge `--no-ff` in both repos and run the project's verification. Green → the ticket has **landed**: `dispatch review <slug>` again, which writes `status: done` and the round's two ranges into the ticket, then `dispatch ctl cleanup <slug>` and `git branch -d` the ticket branch in each repo here; its dependents are on the frontier from here. Red after the merge, or a conflict → abort, `dispatch push` so the host has the tip, and resume the worker with "the branch moved: rebase onto it, resolve, re-verify, report again"; the resume takes the ticket back to `claimed` here, and ticket branches are private, so rebasing them is safe.
  - **Amend** → the user's comments on the page go to the worker as guidance on resume, which takes the ticket back to `claimed`; it revises on the same two branches, reports again, and the ruling comes round again.
  - **Redo** → the build is discarded and the ticket kept: `dispatch ctl cleanup <slug>`, `git branch -D` in both repos here, the ticket reset to `open` with the user's reason under its Comments, and a fresh worker takes it.
  - **Reject** → the ticket and its build go together: `tracker drop <slug>` with the reason in the commit message, `dispatch ctl cleanup <slug>`, `git branch -D` in both repos here.
- **Session unrecoverable** (`gone` in the probe, wedged, context-exhausted) → no special machinery: reset the ticket to `open` and `dispatch ctl cleanup <slug>`; the ticket and its ancestry carry everything a fresh worker needs, by construction.

Where a ticket's done-check is human (UI verification), "green" means whatever automated checks exist; the human pass happens in the QA lane below.

**Punts get filed, never buried.** A worker's closing comment punts a cross-cutting concern, defers to a ticket that hasn't started, names friction it hit (a tooling gap, a missing feedback loop, a slow suite), or leaves an `Assumptions` block with a taste call in it. Every such line is yours to sort, and the sort has four outcomes: fixable now → fix it between waves, in a commit naming what it answers; action-shaped but not now → a **proposed ticket** (`/mx:tracker` says what it carries), with blocking edges where a ticket waits on it, and dispatched in this loop like any other ticket; a question only the user can answer → a `## Questions` item on the ticket it belongs to, or a proposed ticket where no ticket holds it; nothing statable → left, and named as left in the debrief (step 5). The **ruling** on a build is the user's, and `review` is where it waits: the board's needs-me group holds every build in that state and every ticket carrying an open question, which is what the debrief counts and what an orchestrator that restarts reads. A breakdown's slices are `proposed` too and take the ordinary landing announcement, since their ruling is the QA of the slice. Friction with the workflow itself (a skill that misled, a dispatch script that broke) is a proposed ticket like any other, its body saying the fix lives in the plugin. A gap noted in a comment has an audience of zero; announce proposals and new questions in every status report.

**Speculation goes one level deep.** A proposal cut from the build of a filed proposal still in `review` is filed and left unclaimed, its brief naming that proposal, so any orchestrator reads the hold from the ticket file. The depth counts an agent's own readings: a proposal cut from the build of a breakdown's slice is at the first level, since the design under that slice is the user's.

The tick's first half is complete when every exited worker is landed, resumed, or reset.

### 2. Re-evaluate the frontier

`tracker frontier`, read for this ticket's descendants and no other tree's: unclaimed, unblocked, open or proposed, and not needing the user (unblocked means every blocker is `done`, accepted and merged, not merely built; a build in `review` is neither open nor unblocking). A ticket carrying `needs-user` is never a worker's and `spawn` refuses it: it wants the user's own session, so write the ask as a `## Questions` item on it and leave it unclaimed, which is what puts it in the board's needs-me group and takes it off the frontier a worker could take; name it in your status line rather than every tick. Everything else goes to a worker, research and prototypes included, and is ruled on its review page. Landing tickets unblocks new ones, and the human QAs landed slices concurrently, filing findings as new tickets with blocking edges; the frontier absorbs those the same as the originals.

### 3. Plan the wave

Assess parallel-safety now, against the code as it stands: file overlap between two tickets depends on the current tree, so this judgment lives at dispatch time, not when the tickets were cut. Estimate which files each frontier ticket will touch; spawn together only tickets whose edits stay disjoint, and hold the rest for a later wave. When in doubt, serialize the doubtful pair.

File overlap is the mechanical test; **coherence** is the deeper one. Tickets that share one *surface* (one UI, one document, one API façade) produce locally-passing, globally-incoherent work when built in isolation, even where their files barely overlap: give a shared surface to one serial worker. Parallelism is for tickets separated by real seams. Repeated conflicts on one hub file are this warning arriving as a merge statistic: treat it as a structure signal, not a scheduling problem.

### 4. Claim and spawn

**Each ticket's host is picked here, as you spawn it.** Which machines are up and what a ticket needs are facts of this moment, so nothing records a host: `worker-hosts` lists the candidates with their live state, and `worker-hosts <user@host>` prints one's capability record (its toolchain, and what it cannot do at all); the machine you are on is `local`, and where a worker runs when nothing else is reachable. Workers belong on a machine that stays awake; a laptop that suspends kills every worker on it. Read each ticket against the records and place it: a ticket needing a capability no reachable host has is a question on that ticket, never a blocker a worker discovers on arrival. `isolated: true` in the record means the host is itself the boundary around a worker: spawn there with `DISPATCH_PERMISSION_MODE=bypassPermissions`. No record, no claims: default permission mode, and no capability assumed that you haven't verified. Report each ticket's host and its limits to the user.

For each ticket in the wave:

1. `dispatch claim <slug>`: it flips the status and commits it where ticket files are committed (you are the sole claim-writer); the spawn pushes the tip the ticket branch cuts from, so a newly-unblocked ticket gets its blockers' landed code.
2. Write the ticket message (Worker contract) and hand it over: `dispatch prompt <slug> < <file>`.
3. `dispatch ctl --host <host> spawn <slug> <model>` with the host's permission mode in the environment, then arm the watcher: `dispatch wait <slug> --deadline <secs>` as a background task, the deadline being the longest you are willing to go without checking on it. The first spawn on a host stages it (the scripts, the bare repo, the push) and needs `claude` authenticated there with the `mx` plugin installed; a project whose install is neither `make install` nor `nix develop -c make install` also needs `--setup-cmd '<its setup line>'` on that host's first spawn. The worker's model is explicit: Opus by default, Sonnet by your judgment for a small or trivial ticket, never Fable unless the user names it explicitly for this run, and never simply inherited from the orchestrator's own model; the judgment calls (wave planning, merges, verification) stay with you.

### 5. Stop or sleep

**Status is a render, not prose.** Keep chat output to a line or two per tick. The standing status view is the board (`/mx:tracker`): `dispatch review` re-renders it after each landing, and the human's own `board` keeps the tab current in between; never hand-write status prose that can go stale.

What waits on the user is on the tickets themselves, as `## Questions` items the board's needs-me group shows. Write each so the user can act without a chat round-trip: the decision's context and its options in the question's detail, and anything longer, the kickoff prompt of a session only they can start, in the ticket's body, which the row folds open.

A ticket with no child tickets has no close-out: the loop ends when it lands, or when it is in `review` and its branch waits for the ruling.

Frontier empty and every child ticket landed → close the ticket out, in order:

1. Run the full suite once more on the branch you hold, and grep the properties directory for expected failures (`/mx:testing`): one left names a child ticket that never lifted it, and goes back to that ticket's worker before anything else.
2. **The review one level up**: a full `/mx:code-review` of this ticket's branch against the branch it cut from, with the ticket's own context as the spec axis, since no child was reviewed against the whole and that is where incoherence between them shows. It runs as one more child ticket, filed `open` (the flow's own step, not a proposal), its body naming the range, then claimed and spawned like any other; its worker reviews, fixes and aggregates under the same rule as any review, and you integrate its branch as usual. That ticket on disk is the record the pass ran.
3. `make harden ARGS="--integration-branch <the branch this one cut from>"` once from the worktree, so the range is this tree since it forked rather than everything the branch above is ahead of the default branch by (`/mx:testing`). **The report is yours to read, not the user's**, and every line of it takes the sort of step 1: fixable now is a survivor a test can pin or an uncovered line a test can reach; a proposed ticket is a survivor whose fix is a design change, an unmeasured change, an uncovered line that wants restructuring. Those proposals go round the loop like any other, their own proposals held one level down, and the close-out resumes at the debrief when the frontier empties again; 1 to 3 run once per close-out.
4. The **debrief**, in three parts: the commits that fixed, the proposed tickets by slug with their review pages, and what was left with its reason. You report it in chat, since the user is at the end of the work with you; every call in it that is theirs to make goes on the ticket it belongs to as a question, or a proposed ticket where none holds it (the tick's step 1), so nothing waits on them in chat alone. The diff already carries the proposed ticket files and the raw report stays with you. The rulings land the accepted tickets and drop the rejected with their builds (`/mx:tracker`); the merge commit body records them and what was left.
5. Start the fuzz run on the worker host, `dispatch ctl fuzz start`, and tell the user its session name and how to attach. It runs until you or they stop it (`dispatch ctl fuzz stop`), which retiring the ticket includes; so does ruling every proposed ticket (`/mx:tracker`, Retire). Then stop the loop.

Frontier empty with tickets left, every one needing the user, a build in `review`, or blocked on one of those → the work waits on the human: report which questions and rulings, and stop the loop; the answers reopen it.

Otherwise the watchers are your wake signal. `dispatch wait` returns within seconds of a worker's exit, and returns on its `--deadline` when nothing has happened by then, which a plain wait would sit through until the session ended. A watcher back on its deadline hands you a decision rather than a finished worker. Read the pane, then resume the worker, stop it, or re-arm with a longer window.

## Worker contract

The contract itself is [`worker-prompt.md`](worker-prompt.md), which the runner appends to every worker's system prompt. What you write is the ticket, and nothing else about the dispatch: a worker's obligations are the same whatever spawned it.

```
Work the ticket <slug>; its context is under this message.
You own only this worktree and the two branches it holds, the code repo's and the agent repo's at `agent/`, both cut from <base>; every other branch, and every ticket file, is the orchestrator's.
Your final act, once the implementation is committed and verified: commit your report at agent/show/<slug>/report.md.
```

The committed report as the *last* act is what says the run left something to review; a worker that exits without one gets resumed, and one whose report opens with a blocker is read against that blocker.

## Intervening and observing

- **Guidance**: `dispatch ctl stop <slug>` when a worker needs to hear something now (the branch moved under it, the user changed a ruling); write the guidance with `dispatch prompt`; `dispatch ctl resume <slug> <model>`; arm a watcher on it. A resume restores the worker's whole conversation, so it holds its own commits, edits and stopping point in far more detail than your reading of its scrollback gives you, and it can read anything in the repo for itself. What it lacks is a reason to look. Guidance is an instruction to act on something that shifted while it was stopped ("the branch moved: rebase onto it"); when nothing did, `continue` is the entire message. Recapping the worker's own state to it overwrites better knowledge with worse.
- **Observe**: `tmux capture-pane -p -J -t <session> -S -100` on the host (the probe names the session); the human attaches with `tmux attach -t <session>`, over ssh with `-t`.
- **After an orchestrator restart** (your session crashed, or a new one took over): watchers were background tasks of *your* session and died with it, while the workers kept running. `dispatch ctl probe`, then arm a watcher per `running` worker; the same two steps when a watcher fails on an unreachable host. Nothing else needs reconstructing: claims live in ticket frontmatter, work and reports on ticket branches, runs in the host's manifest.
